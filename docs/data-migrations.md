# F02 数据迁移与兼容约定

## 当前范围

F02 按 1 至 9 顺序实施，各项检查通过后才进入下一项。远程 CI 仍待验收。
本功能继续使用 SQLite，不引入后台任务持久化或 F03。

## F02-1 数据清单

源码结构快照为 [无版本业务结构](../tests/fixtures/database-schema-v0.json)。
该快照从 F01 当前源码提取，不依赖真实任务内容，包含 12 张业务表：

| 所属模块 | 表 | 必须保留的内容 |
|---|---|---|
| research_store | research_runs、research_events、writing_evidence | 要求上下文、进度、事件、稿件版本、原始证据与核验结果 |
| research_library | research_candidates、research_library_versions、research_library_current、research_exclusions、research_garbage | 恢复候选、不可变来源版本、当前视图、人工排除、回收队列 |
| research_budget | research_search_attempts | 搜索次数及章节归属，升级不能重置额度 |
| diagnostics | run_diagnostics | 事件顺序、请求指标、使用量 |
| advisor | advisor_exchanges | 问题、回答、失败原因、中断归属与时间 |
| delivery | completion_records | 正文内容哈希和完成确认时间 |

业务表中的 data 为各模块管理的 JSON，不在 F02 中任意重写。
正文、要求、材料提取文本、版本历史、人工决定和待处理内容保存在 RunState；
其 schema_version 当前为 1，与数据库业务表版本分别管理。

LangGraph 管理 checkpoints、writes 两张表及其序列化格式；本项目不直接修改
检查点 BLOB、执行游标、interrupt ID 或 pending writes。依赖结构兼容检查必须
先于 SqliteSaver 的自动初始化；业务迁移事务不调用其 setup/executescript。

## 支持的历史结构

- 空库与尚未创建的数据库。
- 当前无版本业务表的合法子集：历史版本按需建表，缺少整张可选业务表不等于损坏。
- 现有回归中的 research_entries 混合来源表：列与 research_candidates 对应；
  迁移时按 writing_evidence 重建正式历史，保留恢复候选及原始文件。
- 当前检查点结构，以及依赖源码明确支持的 writes 缺少 task_path 列的结构。
- 结构字段符合当前 RunState 校验规则的无 schema_version 状态，解释为 v1；
  不把未知字段、未知显式版本或损坏数据当作已知历史版本。

未知表、字段、索引或未来迁移版本必须报告并停止，不能凭表名直接认领为当前版本。
不宣称支持尚无样本和转换规则的其他历史发布版本。

## 文件依赖与恢复边界

- research-assets：PDF、图片、网页和来源证据 JSON，文件名及业务引用包含哈希。
- skill-snapshots：Skill 文档快照及清单，RunState.skill_root 可能为绝对路径。
- 上传和 CLI 材料：RunState.materials 保存原路径、文件哈希和完整提取文本；
  CLI 原文件允许位于数据库目录以外，不能仅通过扫描 uploads 推断全部依赖。
- 导出 DOCX 可由已验证记录重新生成；API Key 不属于迁移输入，不收集 .env。

数据库备份与外部文件清单须来自停止业务写入后的同一维护窗口。文件恢复不得
覆盖其他任务共享的文件；缺失或哈希不符必须明确报告。恢复副本验证和覆盖原库
是不同操作，不能以备份生成成功代替恢复验收。

## 操作流程

全部命令从项目根目录运行，安装方式沿用 README 的锁定依赖命令。

1. 停止使用目标库的 Web 服务、CLI、旧版本程序及其他写入程序。
2. 执行 `assignment-agent --db <数据库路径> db status` 和 `db plan`；检查不调用模型。
3. 对已知旧库执行 `assignment-agent --db <数据库路径> db migrate --offline`。
   升级前备份成功且经过校验，才执行迁移；可通过 `--backup-directory <新目录>` 指定位置。
4. 核对返回状态、维护报告和 `db status`，再启动业务服务。

`db status` 退出 0 表示诊断命令成功，不表示结构兼容；应检查 JSON 的 status。
`db plan` 对未知结构、损坏数据、未来版本和签名冲突返回非零退出码。
缺失/空库可初始化，旧无版本库必须显式升级；未来版本不尝试降级。

## 备份格式和恢复

备份含 database.sqlite、manifest.json、平铺的 objects/<SHA256> 对象。
清单保存文件原路径、恢复相对路径、对象位置和哈希，不收集 .env 或 API Key。
支持读取早期测试布局的 files/<相对路径> 清单；其内容仍须通过完整哈希验证。
数据库使用 sqlite3.Connection.backup，不能要求备份文件的 SQLite 页头与源库逐字节相同；
完整性检查、全部逻辑结构/数据和恢复后的业务行为才是验收依据。

`assignment-agent --db <数据库路径> db backup <新备份目录> --offline` 生成手动备份。
`assignment-agent db restore <备份目录> <不存在的恢复目录>` 先校验，再生成独立副本。
恢复保留数据库原文件名，并生成同名 .paths.json 路径映射，不能单独丢弃此文件。
材料原文件和 Skill 快照在读取状态时映射到恢复目录；历史检查点不重写。
二次备份恢复仍保留原始历史路径映射。恢复目标不要手动搬动，需要换目录时重新恢复。

本轮所有真实升级演练在临时数据库或副本进行，未升级 workspace 根目录的实际任务库。
实际部署应先运行只读计划；不能把测试副本成功等同于所有未知历史库均兼容。

## 失败处理

- 备份失败、材料或 Skill 文件缺失/哈希不符：不开始迁移，修复原因后使用新备份目录重试。
- 当前步骤异常或进程终止：该步骤的表、数据和成功记录一起回滚；此前提交的步骤保留。
  重启后依据迁移记录跳过已完成步骤；中断进程可能只留下 started/不完整报告，应核对数据库。
- 已提交升级需要撤回：停止业务，从升级前备份恢复到独立目录，验证后使用对应版本程序启动。
  不提供任意版本的逆向 SQL 自动降级，也不自动覆盖原库。
- 未知结构、来源同编号冲突、未来状态或迁移签名变化：停止执行，不直接改版本号绕过检查。
- 本项目维护锁是协作锁：新版本业务共享、维护独占；旧程序和直接 sqlite3 写入者不遵守它，
  所以停服维护仍是必要前提。业务共享锁用于保持原有状态查询能力，不实现 F04 幂等保护。

## 后续迁移编写约定

历史 v001、legacy_v0 和固定 F01 结构定义不可原地修改；变更新建连续编号迁移。
迁移签名覆盖冻结脚本和结构输入，已应用脚本的签名变化必须拒绝。
业务归档函数可独立演进，不得反向改变历史迁移算法。
每个步骤只使用执行器提供的连接，不能自行 commit、使用隐式提交的 executescript，
不能在事务里调用 LangGraph setup，也不能在 SQL 提交前删除外部文件。
新增版本需同步扩展只读结构识别、兼容规则、故障注入和端到端回归。
